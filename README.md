# GodForge

GodForge is a **SMITE 2 Discord match-orchestration bot** for communities running pickup games, inhouses, scrims, and draft nights.

It combines lightweight public commands with durable party/lobby workflows, ready checks, temporary match spaces, team formation, drafting, result tracking, and reusable match records.

> **Status:** Active release-candidate development. Core Discord party and draft workflows are implemented; the companion web dashboard/API bridge remains a staging surface.

## What GodForge Does

### Party and lobby operations

- Provisions a managed Play channel and temporary-room category with `/party setup`
- Lets players save preferred roles and join queues with low-friction controls
- Supports concurrent isolated queues, waitlists, and role-aware promotion
- Runs ready checks with Ready / Need 5 Minutes / Drop responses
- Creates private match workspaces and optional team voice channels
- Supports organizer room controls without broadly granting `Manage Channels`
- Stores immutable guild-scoped room reports when a match space closes

### Scheduled game nights and scrims

- Creates one-time or recurring pickup nights
- Publishes persistent RSVP cards with saved-role support
- Rolls weekly RSVP surfaces forward instead of reposting new cards
- Supports premade-team scrim setup, challenge, and launch flows
- Reuses the same lobby, room, draft, and result infrastructure across game-night types

### Team formation and results

- Forms 1v1 through 5v5 teams from ready rosters
- Supports role-fit, balanced, and captain-team approaches
- Tracks standalone match outcomes with captain confirmation and organizer dispute handling
- Records guild/team/player game-night history and basic participation statistics

### Draft and randomizer tools

GodForge also includes its original SMITE utility surface:

- random god and build commands;
- channel-scoped draft sessions;
- fearless draft sets;
- portable Draft JSON export;
- optional ForgeLens-compatible handoff.

ForgeLens integration is optional and disabled by default. GodForge remains usable as a standalone product.

## Architecture at a Glance

```text
Discord
  ├─ party / schedule / scrim workflows ──► durable SQLite lifecycle state
  ├─ randomizer / build commands ─────────► versioned local content data
  └─ draft workflows ─────────────────────► portable match/draft records

Optional web dashboard/API bridge
  └─ local or staged admin surfaces
```

New durable workflows should treat Discord messages and components as interaction surfaces rather than the only source of truth.

## Quick Start

### Requirements

- Python 3.11+
- Discord bot token
- Message Content Intent
- Server Members Intent for role/member-dependent behavior
- Discord permissions required by the workflows being enabled

### Install

```bash
pip install -r requirements.txt
```

For development/testing dependencies:

```bash
pip install -r requirements-dev.txt
```

### Run the bot

```bash
python bot.py
```

The combined Railway process can be started with:

```bash
python railway_app.py
```

## Key Commands

GodForge intentionally mixes slash commands for durable workflow entry points with legacy dot commands for lightweight randomizer/draft utilities.

Common slash-command entry points include:

- `/party setup`
- `/party reset`
- `/party room`
- `/party report`
- `/party schedule`
- `/scrim team-create`
- `/scrim challenge`
- `/scrim launch`

Legacy utility families include `.rg`, `.roll5`, build commands, `.session`, and `.draft`.

Use `.help` and Discord command discovery for the live command surface. Deep workflow behavior belongs in project docs rather than being duplicated here.

## Storage and Content Contracts

Party lifecycle state is stored in SQLite. Production deployments should place durable databases on persistent storage.

SMITE god/build content is versioned in repository data files. Build artifacts generated by [`diese-tech/smite-content-sync`](https://github.com/diese-tech/smite-content-sync) must remain contract-compatible with GodForge's loaders; restart the process after deploying regenerated content so in-process caches do not serve stale data.

## Design Principles

- **Standalone first:** optional integrations must not become hidden hard dependencies.
- **Durable workflows:** party, room, schedule, and result state should recover safely after restart.
- **Low-friction player UX:** persistent controls and saved preferences should reduce repeated setup.
- **Scoped authorization:** organizer/staff actions are revalidated at execution time.
- **Clear product boundaries:** GodForge owns match orchestration, not league-wide stats, economy, or unrelated moderation.
- **Operational visibility:** partial Discord failures should be diagnosable rather than silently reported as success.
